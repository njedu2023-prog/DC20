# 10:00 出口来源时间语义复核（2026-09-12）

结论：研究任务继续运行，但 `provider_timestamp_semantics_confirmed` 仍为
`false`。本复核没有修改当前采集请求、分钟解释、模型、退出引擎或正式账本。

## 已确认与尚未确认

- [当前 stk_mins 官方文档](https://tushare.pro/document/2?doc_id=370)
  将 `trade_time` 定义为交易时间，但没有明确一分钟的覆盖区间及开始/结束端点。
  09:30、09:31 和 15:00 示例以及实际 240 行网格与 BAR_END 假设相容，
  不等同供应商确认。不能仅凭行数与 SHA 校验将假设改成正式保证。
- [官方 SDK](https://github.com/waditu/tushare/blob/master/tushare/pro/client.py)
  读取服务端 fields/items，没有为 stk_mins 提供时间区间映射。
- [旧分钟说明](https://tushare.pro/document/1?doc_id=234) 描述提取范围及更新方式，
  也不能替当前 stk_mins 定义时间区间。
- [官方仓库问题 #1903](https://github.com/waditu/tushare/issues/1903)
  是用户报告分钟聚合与日线不一致，不是维护者的时间语义声明。

## 为什么影响 10:00 规则

现引擎把标为 10:00 的 bar close 用作该时点决策依据，再取下一 bar open
作为退出代理。如果提供方标签实际代表 bar 开始，这会使名义 10:00 决策
包含之后一分钟信息。数据未损坏不等于时间因果性已独立证明。

这不证明当前数据就是 BAR_START，也不证明已有研究数值必然错误；它限定
当前能够作出的结论。必须保留原始查询参数与原始响应，不能为了通过检查
重命名时间戳或改写旧源元数据。

## 后续可执行的核验

1. 完成当前固定规则、固定样本的 v2 重放；不趁数据尚在采集中更换解释。
2. 必要时另建预注册的双时间解释敏感性回放，两个结果都保留，不选择更赚钱
   的解释作报告；这仍不是供应商确认或正式激活依据。
3. 正式来源确认应覆盖：10:00 bar 的真实区间、09:30 独立记录含义、历史年份
   是否一致、实时 bar 何时结束并可取得。书面答复或明确版本化文档需原样归档。
4. 若当前来源不能确认，可考虑有明确交易所时间和接收时间的逐笔/快照来源，
   但需要单独选择与授权，不能暗中替换数据商或发出外部询问。

## 停牌字段是另一件事

[suspend_d 文档](https://tushare.pro/document/2?doc_id=214) 明确区分日内时段
与空时段；精确代码/日期的 S 空时段支持整日停牌事件解释。它不能补出 OHLC、
成交或收益，也不能证明未查询日期同样停牌。旧诊断归档是 data table 与响应
摘要，不是完整 HTTP 原文；后续导入必须保留这种来源差异。

停牌事件的语义确认不能消除 stk_mins 的时间语义门槛；两个来源必须分别验收。
